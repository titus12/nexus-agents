# 中书省组级收敛与产物形态需求

> 2026-09-26 修订：审核与修订单元由 item 改为组（§2/§4/§5/§6/§9/§13/§14），引入整组裁决、组内 patch 冻结区与 §8 机械投影闭包；实施安排见 `docs/superpowers/plans/2026-09-26-zhongshu-group-pipeline-implementation-plan.md`。

## 1. 背景

中书省现行审查循环中，审查与收敛的粒度不对称：

- 审查已按任务（item）粒度执行：Critic 以 task_review wave 逐 item 派发，判定折叠进 `task_review_ledger`（`states.py` 的 `_task_review_bindings` / `_task_review_ledger_update`）；
- 修订与收敛是全图粒度：一个全局 `zhongshu_revision_round`、一个全图 `blocker_fingerprint`（`policies/zhongshu.py:391`）、全部 item 过审才允许冻结（`unapproved_item_ids`，`states.py` 的 `ZHONGSHU_FREEZE_INCOMPLETE`）。

这种方式存在以下问题（有实证）：

- 一个顽固 item 烧全图预算：9/10 过审也冻结不了，`ZHONGSHU_FREEZE_INCOMPLETE` 直接人闸，整图为一个组陪葬；
- 全图指纹误伤：一个组打转时，其他组本来在收敛的进展也被判"无进展"（task-20260920-94c51b：critic → analyst → solver 无界循环）；
- 同一意见被反复铸造新 finding id：task-20260920-bbd659 中 3 个真实 issue 被铸出 7 个 finding_id（含跨语言重述）；
- 已收敛组不能提前放行：门下省已于 2026-09-23 完成组级流水线重构（`docs/2026-09-23-menxia-group-pipeline-acceptance.md`），两条流水线完全串行，门下省无法提前接手已收敛的组；
- 修订无对账：批次由编排器选定（`select_solver_batch`），但回包是否逐条处理了批次内 finding 没有机械校验，critic 重审是唯一确认手段；
- 修订无冻结区：未入选批次的 item 正文可被修订回包改动，靠下一轮 critic 发现。

产物形态上同样有缺口：

- 中书省冻结产物是单一任务图（groups + items 字段），组的"需求"散落在 item 的 `title`/`objective`/`acceptance_signals` 里，没有成文的需求文档：背景与痛点、责任边界、非目标、场景化行为要求无处安放，critic 审查与门下省审议缺少锚点（menxia 验收文档 §5.6 所述 anchor 盲区的根源）；
- 门下省组文档五节结构中，正文（body）由 solver 自由组织，未规定必须呈现"已定稿的实施方案"：是否存在未决设计选择、现状断言是否有据、验收是否被覆盖，都无强制落点。

本需求要求：以组为粒度重建收敛记账、裁决与修订对账（审查粒度对齐到组，消除上述不对称），并**重构两级产物的目标形态**——中书省冻结产物为每组一份需求文档，门下省组文档正文为一份可实施方案。

## 2. 目标

1. 组是中书省记账、裁决与修订的唯一原子：修订预算、停滞判定、批准状态均按组登记，审核与修订的派发单位亦为组；item 仅作为 finding 归属与证据路由的坐标，不再是裁决单元；
2. 组间隔离：一个组停滞或预算耗尽，不消耗其他组的预算，不阻塞其他组冻结；
3. 增量冻结：已收敛且依赖已冻结的组可以先冻结，门下省提前接手该组；
4. 修订对账：批次内每个 finding 必须有采纳或驳回的处置记录，缺记录的回包整包拒绝；
5. 冻结区保护（两层）：组内——批次 finding 未归属的成员 item 正文不可被修订回包改动；跨组——非本组的 items 与组需求文档逐字保留；越界改动一律机械拒绝；
6. 输入自足：每轮派发包含 worker 作出判断所需的权威内容，不依赖重读历史评论或外部 artifact；
7. 中书省冻结产物重构为**每组一份需求文档**（§9），结构机械可查，是审议与验收的唯一锚点来源；`acceptance_signals` 由 §8 机械投影，闭包由构造保证；
8. 门下省组文档正文重构为**可实施方案形态**（§10），收敛判定包含对其结构的机械校验。

## 3. 组与冻结的标识

组身份由任务图中的 group 定义。同一组的身份在其存续期内保持稳定：

- 同一 group_id 下的 item 增删、依赖调整必须通过显式动作申报，不得以修订正文的方式变相实现；
- `REQUEST_REGROUP` 重划组后，组身份重新确立：旧组账本关闭归档，不迁移到新组；新组从初始状态重新记账，其需求文档从新版任务图重新生成。

组依赖即任务图的依赖边。"依赖已冻结"指该组的全部直接依赖组均处于 FROZEN 状态（无依赖的组视为满足）。

## 4. 组收敛状态语义

每个组处于以下封闭状态之一：

| 状态 | 判定 |
|---|---|
| `REVIEWING` | 该组待审或待修（组面 hash 与上次裁决时不一致），或组内存在未决 finding |
| `CONVERGED` | 组审裁决为 `APPROVE_GROUP`（组面 hash 未变的重审沿用棘轮），且组内无 open P0/P1 finding；ledger 全成员 APPROVED 是该裁决的机械投影 |
| `FROZEN` | 已通过组级冻结检查并发布给门下省 |
| `STALLED` | 停滞或预算耗尽，待人闸 |
| `BLOCKED` | 因协议违规或不可恢复错误停机 |

判定规则：

- **停滞**：组内 open P0/P1 blocker 计数连续 2 轮修订后未下降（首轮修订只记基线，不判停滞）；
- **预算**：每轮修订消耗 1 次，组级上限 5（与门下省组级预算一致）；耗尽即 STALLED；
- **组面棘轮**：组面 hash = (doc_hash, sorted[成员 task_hash])；hash 未变的组不再派发审核任务（`ZHONGSHU_GROUP_APPROVAL_HELD`），任一成员正文或文档版本变更即失效；
- **组冻结检查**：CONVERGED 且依赖已冻结的组，逐组执行冻结检查（`02-zhongshu-protocol.md` §5 的各校验项 + §9 的产物形态校验按组投影执行）；全图校验项（依赖无环、全局 P0/P1 清理）在该任务图首个组冻结前完成一次；
- 组状态变化只由折叠结果驱动，不由 worker 声明。

## 5. 修订与对账行为要求

### 5.1 有 finding 的修订轮

1. 修订批次由编排器选定并**按组切分**：一轮修订波对每个受影响组并发派发一个 solver worker（跨组并行），worker 不自行挑选要修的 finding；
2. worker 的可编辑面 = 批次 finding 所属 items + 本组需求文档；其余成员 item 正文逐字保留（组内 patch 冻结区，见 §5.3）；
3. 批次内每个 finding 必须有处置记录：采纳（说明如何解决、落到哪个 item、恢复哪个验收项）或驳回（给出理由）；
4. 缺处置记录的回包整包拒绝，不进入折叠，走既有 reply-retry 预算；
5. P0/P1 的驳回必须经提出方 Critic 确认后才销账；P2/P3 的驳回一轮无异议即自动销账；
6. 处置记录与销账状态由编排器登记并机械对账（吸收即删、留痕账本语义与门下省组文档一致）。

### 5.2 组裁决

组审只出一个组级裁决（`APPROVE_GROUP` / `REVISE_GROUP` / `REQUEST_ANALYST_EVIDENCE` / `HUMAN_GATE` / `BLOCKED`）：

- `APPROVE_GROUP` ⇒ 全成员 item 在 ledger 中机械投影为 APPROVED，组转入 CONVERGED；
- `REVISE_GROUP` ⇒ 整组回炉：组 `revision_round+1`，全成员投影为 CHANGES_REQUIRED，进入组修订波；
- finding 仍按 `item_id` 归属，仅用于修订定位、证据路由与停滞统计，不构成独立裁决；
- 不再为确认性重审额外消耗轮次：组面 hash 未变时棘轮沿用上次裁决。

### 5.3 冻结区

冻结区分两层：

- **组内**：批次 finding 未归属的成员 item 正文（目标、范围、验收信号）逐字保留；
- **跨组**：非本组的 items 与非本组需求文档逐字保留（含文档版本比对，沿用 `SOLVER_GROUP_DOC_FROZEN` 语义）。

- 修订回包改动任一层冻结区内容 → 机械拒绝，附违规明细；
- 新增、删除、移动 item 必须走显式动作，机械拒绝不得以"修订"名义替代。

### 5.4 全图操作

`REQUEST_REGROUP` 与 `REQUEST_ANALYST_EVIDENCE` 保持全图语义。regroup 后全部组账本重新播种；证据轮不消耗任何组的修订预算。

## 6. 输入自足要求

每轮派发必须让 worker 不读历史评论或外部 artifact 即可作出判断：

- 派发给 solver（按受影响组，跨组并发）：本组批次 finding 全文、本组 items 正文、本组需求文档全文、上轮处置记录；
- 派发给 critic（按组）：组需求文档全文、全部成员 item 的正文与验收信号、归组 finding、各成员 item 的证据切片；未变更成员可投影为摘要 + hash（增量胶囊），变更成员必须带全文；
- 同一意见的重复表述由编排器按内容身份归并，critic 不得通过铸造新 finding id 表达旧意见。

## 7. 人闸与恢复要求

1. **波次收尾拦截**：一轮波次收尾时，若剩余未收敛组全部处于 STALLED/BLOCKED，直接人闸并列出各组未决事项，不再重派；
2. **定向解停**：人闸的修订决定必须指名组；被指名组的预算归零并恢复，未指名组不受影响、不重开。

## 8. 责任边界

编排器负责：批次选定、销账对账、冻结区比对、组状态登记、产物形态校验（§9.3 / §10.3）。

solver 不再负责：

- 挑选要修的 finding；
- 自行决定修订范围（超出批次即越界）；
- 通过改写未授权 item 变相增删任务；
- 自由组织门下省正文的呈现结构（§10.2 规定的部分逐节齐备）。

critic 不再负责：

- 为同一意见铸造新 finding id；
- 无法锚定的主观意见（必须锚定 §9 需求文档的具体条目，见 §11.2）。

## 9. 中书省产出目标形态：需求文档

**重构内容**：冻结产物从"单一任务图 + 零散字段"重构为"任务图 + **每组一份需求文档**"。需求文档是该组审议、验收、返工的唯一锚点来源，结构九节、节序固定：

| 节 | 内容要求 | 质量红线 |
|---|---|---|
| 1 背景 | 现状行为与痛点枚举 | 每条痛点锚定具体代码位置或可复现行为，不接受泛化抱怨 |
| 2 目标 | 编号的行为目标 | 每条可判定："只能存在一个""恰好一次""不得回写过期状态"句式；禁止"尽量""应该更好" |
| 3 标识与范围 | 本组处理对象的身份定义与归属分类 | 身份封闭：哪些输入属于本组、哪些不属于，逐条列明 |
| 4 状态与边界语义 | 相关状态的封闭枚举与判定规则 | 逐状态给判定，不留"其他情况酌情处理" |
| 5 行为要求 | 按场景分节；每个场景列出行为与各下游的通知规则 | 场景封闭覆盖：目标中每条行为可归入唯一场景 |
| 6 责任边界 | 上下游职责的正面与负面清单 | "谁不再负责什么"必须显式成文 |
| 7 交叉不变量 | 防绕过条款（如"某开关关闭时本组目标仍须成立"） | 每条不变量可独立验收 |
| 8 验收标准 | 独立成节，按成员 item 分小节（`### <item_id>`），小节内按场景分组 | 每条为可观察断言；本节是 item `acceptance_signals` 的唯一作者（机械投影来源） |
| 9 非目标 | 封闭排除列表 | 与目标节无交集，排除项逐条列举 |

### 9.2 与现有模型的衔接

- 组需求文档随冻结版本持久化，并随每轮门下省派发完整传递（沿用组文档权威正文随行的既有语义）；
- 组文档版本随冻结版本演进：返工出新版本后版本号递增、门下省从新版本重新起步；
- `acceptance_signals` 是第 8 节的机械投影：编排器解析 §8 的成员 item 小节逐条投影到对应 item，plan 中该字段不再由 solver 自由撰写（模型所写一律被投影覆盖）；§8 与 `acceptance_signals` 的双向闭包由构造保证；
- 机械形态校验（九节齐备、措辞黑名单、依赖无环、无实现词）在派发前以 LLM-free 预检执行：预检不过的组不派发审核轮，直接路由修订，拒绝反馈必须附期望内容 diff（缺哪行/多哪行/哪句违规）。

### 9.3 机械检验点（冻结检查逐条执行）

1. 九节齐备、节序固定（结构校验，与门下省 `verify_group_reply` 的节完整性检查同构）；
2. 第 2 节每条可判定、第 8 节每条可观察（措辞与句式校验）；
3. 第 8 节与 item `acceptance_signals` 双向闭合（投影构造保证，冻结检查复核投影结果）：无孤儿验收标准、无无验收的 item；
4. 全文无实现词汇（实现设计只允许出现在门下省产物）；
5. 任一项不过 → 拒绝冻结，附未过项明细。

## 10. 门下省产出目标形态：可实施方案

**重构内容**：组文档正文（body）从 solver 自由组织重构为**可实施方案形态**——目标是"所有设计选择已定稿，实施时按任务顺序执行，不再需要额外决策"。结构六部分：

| 部分 | 内容要求 | 质量红线 |
|---|---|---|
| 头部 | 需求来源（组需求文档版本引用）、零决策声明、Goal 复述、设计决策列表、"不改动"清单 | Goal 只复述不重定义；每条设计决策可追溯到需求条目；"不改动"镜像需求第 9 节 |
| 现状与目标行为表 | 场景 × 当前行为 × 目标行为 × 实现归属 | 每条现状断言带代码锚点；每个场景有实现归属，无孤儿场景 |
| 统一约束 | 跨任务的横切约束 | 与需求第 7 节不变量一致 |
| 任务分解 | 逐任务：分类（缺陷修复/行为变更/回归保护）、涉及文件、验证方式（红测试先行及预期红断言）、实现要点、副作用核实、回归保护清单 | 先测试后实现；预期红必须写明断言值；例外必须记录 |
| 验收映射 | 需求第 8 节验收项 ↔ 覆盖测试的双向表 | 正向无漏覆盖、反向无孤儿测试 |
| 风险与兼容 | 行为变化、兼容影响、回滚方式 | 与需求第 9 节不冲突 |

### 10.2 与五节文档模型的衔接

- 头部、现状表、统一约束、任务分解、验收映射、风险与兼容 = body（冻结区）；
- critic 意见仍走建议段与吸收账本（生命周期规则不变）；
- 双签与 signoff 语义不变。

### 10.3 机械检验点（critic 收敛判定逐条执行）

1. 六部分齐备（结构校验）；
2. 验收映射闭合（并入既有 joiner 收敛前置检查：不闭合不得 APPROVE_GROUP）；
3. 零遗留决策：存在未定稿的设计选择即不得 APPROVE_GROUP；
4. 每条例外（不可观测项、无法覆盖项）具备三要素：例外原因、替代验证手段、补测触发条件；
5. 现状断言的代码锚点抽查：抽查不过按 content 失败降级 BLOCKED（anchor 盲区的机械缓解）。

## 11. 产物间追溯关系

1. 门下省验收映射的左侧条目只能来自需求文档第 8 节；
2. critic finding 必须锚定需求文档第 2/7/8/9 节的具体条目（目标违反 / 不变量违反 / 验收缺口 / 越界），无法锚定的意见降级为 P2/P3 建议，不阻断收敛；
3. solver 吸收修订时，处置记录必须指明所影响的任务与所恢复的验收项；
4. 需求文档版本与冻结版本绑定：门下省审议期间需求文档不可变，返工出新版本后门下省从新版本重新起步（沿用既有"灶台不改谱"边界）。

## 12. 边界不变量

1. 组记账在门下省并行关闭（serial 路径）下同样成立；
2. fast_track 下不存在审查轮，组记账不适用、不产生组状态；
3. 组一旦 FROZEN，后续针对该组的 finding 只能经门下省回路产生并退回中书省出新版本，不得回改已冻结产物；
4. 增量冻结不改变 GATE、ESCALATED、HUMAN_GATE 的既有语义与通知文案结构。

## 13. 验收标准

### 单组收敛

- 仅组 A 有 finding、组 B 无：组 B 先转入 CONVERGED 并可冻结，门下省先接手组 B；
- 组 B 的收敛不消耗组 A 的修订预算。

### 顽固组隔离

- 组 A 磨至预算耗尽：组 A 转 STALLED 人闸；组 B 照常冻结、照常在门下省推进至完成；
- 组 A 的 open blocker 计数变化不影响组 B 的停滞判定。

### 组级停滞

- 组内 open blocker 计数连续 2 轮不降：该组 ESCALATED 人闸，不空转重派；
- 首轮修订只记基线，不触发升级。

### 修订对账

- solver 回包缺任一批次 finding 的处置记录：整包拒绝，不折叠，走 reply-retry 预算；
- P0/P1 驳回未经提出方确认：不销账，下一轮批次仍包含该 finding；
- P2/P3 驳回一轮无异议：自动销账。

### 组裁决与投影闭包（2026-09-26 修订）

- 组审一个组级裁决落账：`APPROVE_GROUP` ⇒ 全成员 APPROVED 投影、组转 CONVERGED；`REVISE_GROUP` ⇒ 整组回炉，组修订轮 +1；
- §8 ↔ `acceptance_signals` 闭包由投影构造保证：孤儿验收标准类拒绝零发生（投影后闭包校验恒真）；
- 机械形态违规零 LLM 轮：预检在派发前拦截，预检不过的组不派审核任务，直接路由修订并附期望 diff；
- 多组同时需要修订时，修订波跨组并发派发（每组一个 solver worker）；
- 组面 hash 未变的组零派发（`ZHONGSHU_GROUP_APPROVAL_HELD`）；变更成员或文档版本即失效；
- 组内 patch 冻结区：修订回包改写批次未归属的成员 item → 机械拒绝；跨组越界 → 机械拒绝。

### 冻结区保护

- 修订回包改动组内未归属 item 正文或跨组内容：机械拒绝，附违规明细；
- 以修订名义增删 item 而不走显式动作：机械拒绝。

### regroup

- 重划组后：旧组账本关闭归档，新组从初始状态记账，新旧组账本无串组。

### 定向解停

- 人闸修订指名组 A：组 A 预算归零恢复，组 B 状态与预算不变。

### 需求文档形态（§9）

- 冻结产物每组一份需求文档，九节齐备、节序固定；缺节或节序错误 → 冻结拒绝并附明细；
- 第 2 节出现"尽量""应该更好"类不可判定措辞 → 冻结拒绝；
- 第 8 节验收项与 `acceptance_signals` 不闭合（存在孤儿验收标准或无验收 item）→ 冻结拒绝；
- 需求文档含实现词汇 → 冻结拒绝。

### 可实施方案形态（§10）

- 组文档 body 六部分齐备；缺部分 → critic 不得 APPROVE_GROUP；
- 验收映射不闭合（漏覆盖或孤儿测试）→ 不得 APPROVE_GROUP；
- 存在未定稿设计选择 → 不得 APPROVE_GROUP；
- 例外缺三要素（原因/替代验证/补测触发条件）→ 不得 APPROVE_GROUP；
- 现状断言锚点抽查不过 → 降级 BLOCKED 并附违规明细。

### 输入自足

- solver 与 critic 派发上下文包含 §6 所列内容；断言派发 bundle 内含组需求文档全文与权威正文，无对历史评论或 artifact 的读取依赖。

## 14. 非目标

本需求暂不包含：

- 修改门下省组级流水线的已验收机制语义（文档生命周期规则、销账规则、stall 阈值、P2/P3 自动销、组级 GATE 行为）；
- 修改 fast_track 语义；
- 修改 finding 严重度定义与 GATE/ESCALATED 的通知文案结构；
- 引入 item 级乱序流水线（推进保持现有阶段模型；item 仅作为 finding 归属与证据路由坐标，不恢复 item 级裁决）;
- 跨 run 的持久化或历史快照迁移；
- 规定需求文档与实施方案的写作文风、篇幅上限；
- 规定现状断言代码锚点的核实层级（L2/单测/审查的选择留给实施方案）。
