# Canonical PlanRevision：实现、验证与自审记录

日期：2026-10-06。本次完成已批准重构的第二阶段；第一阶段结构门禁与分组修复见 `orchestrator-structure-repair-validation-20261006.md`。

## 本阶段结果

新增 `canonical-v1`，以不可变 `PlanRevision` 为正式方案的权威来源。Solver 产生结构化草案，编译器校验后，由 `apply_review_update` 一次提交版本、完整方案、内容哈希、任务投影和分组需求文档。模型返回的 Markdown 不再反写验收条件。

每个版本保存 schema、policy、递增序号、父版本引用、完整结构化内容和 SHA-256。业务内容相同的重复提交复用当前版本；业务内容回退到旧内容也会产生新的版本。模型必须基于派发时的版本工作，过期结果进入既有的有限重试，不能覆盖当前方案。

文档按照现有九章节协议生成，保留需求原文、任务的扩展业务字段和逐字验收文本。生成器的 source hash 包含相关组、成员、需求以及全局方案元数据。未改变的组保留文档字节、版本和审核状态；改变的组清除批准并递增文档版本。冻结组的完整输入不得被普通提交改变。

保留当前人工审核位置。人工审核包额外绑定 `plan_revision_ref`；同内容的新版本也不能复用旧批准。人工退回仍走原有的完整修订入口，机械验证通过后回到人工审核。这里没有实施第三阶段的工序重排，也没有改变人工批准策略。

## 入口与兼容

仅新任务可以显式选择新模式，例如：

```powershell
python D:\workspace\src\nexus-agents\cmd\review_orchestrator_v2.py --new "将需求拆解并形成可执行方案：填写具体需求" --project "1e41be52-4460-4fba-9360-0c60cfc18c92" --plan-schema canonical-v1
```

这是新任务入口示例，本次没有执行该在线命令。

- 默认仍为 `legacy-v1`。旧快照缺少新增字段时保持旧模式，不自动迁移。
- `--resume`、`--cancel`、`--inspect-task` 不能携带 `--plan-schema` 改写模式。恢复使用持久化选择；未知 schema 或 policy 会拒绝加载。
- Canonical Solver 始终通过单个写入者派发，既有分组和单任务修订并行开关不会绕过提交边界。Critic 和下游已有审核工序继续使用当前机制。
- 传输层在正常结果与远程失败后挽救的结果中，都从可信派发上下文写入基准版本，覆盖模型自报版本。
- 普通修订仅开放指定 findings 的任务及相关组内容；新增任务、重分组、改全局范围需走已授权的完整修订入口。单独改投影不能修改业务字段。
- 保存时检查方案哈希、任务与需求投影、生成文档及其 source hash。正式版本产物也包含可验证的 PlanRevision 信封；旧模式产物格式保持原样。

## 无模型验证

使用 `cmd/run_tests.py`，禁止真实飞书及其他外部通知。Windows 临时目录测试在批准的文件访问权限下运行。没有调用在线模型，没有重启或占用 Nexus 的 8766 端口，没有恢复或改写已有在线任务。

新增 `cmd/test_canonical_plan_revision.py`，共 25 项测试，包括三个真实 `OrchestratorApp` 脚本链路：

1. 需求入口 → Canonical 首次提交 → 自动生成文档 → 既有审核工序 → DONE；模型伪造的版本号被传输层覆盖，版本产物与状态一致。
2. Critic 提出定向修订 → 单写 Solver 修改结构化验收条件 → 版本 2 → 复审 → DONE；开启旧并行选项也不能进入旧分组/单任务写路径。
3. 需求入口 → 人工审核 → 退回修订 → 版本 2 的新审核包 → 保存恢复 → 重新批准 → DONE；首次批准包不能替代第二次批准。

其他测试覆盖深层数据隔离、内容幂等、父版本、缺失/过期基准、重复 ID、需求基线、冻结输入、投影写入拒绝、证据更新、Markdown 反写拒绝、同内容新版本批准失效、JSON 类型身份、损坏快照和正常/挽救传输结果。

相关旧机制对照回归：128 项通过，23.302 秒（包含当时的 23 项 canonical 测试）。最终新增模块单独验证：25 项通过，4.455 秒。自审修复后的最终全量验证：1428 项通过，68.006 秒，退出码 0。`git diff --check` 通过，CLI 帮助包含新模式选项。

## 单独自审及修复

实现通过集成链路后，单独检查提交入口、状态折叠、并行入口、传输结果绑定、持久化恢复、产物和人工批准。发现的问题均在提交前修复。

| 阶段 | 问题 | 修复与证据 |
| --- | --- | --- |
| 集成 | 生成标题未带现有协议的版本，文档门禁持续退回 | 生成正确标题并绑定实际文档版本；真实完整应用链路通过。 |
| 集成 | 生成文档给验收行附加列表符号，下游按原文匹配导致反复退回 | §8 直接输出结构化验收原文；人工修订后完整下游链路通过。 |
| 集成 | 扩大通用重试分类会改变旧任务的结构错误处理 | 撤回通用行为变更，仅 canonical 回复形状使用有限重试；旧策略与 FSM 对照测试通过。 |
| 集成/自审 | 改变文档来源时，重新生成可能清掉已机械验证的人工作业冻结状态 | 仅可信 `human_revision_validated` 分支可保留新冻结状态，仍清除旧批准；修订、恢复与新批准链路通过。 |
| 自审 | 空 finding 范围被旧代码解释成全量可修改；普通修订可能重分组或改全局字段 | Canonical 范围用显式空集合，已有正式方案强制按修订规则处理；补测空范围与拓扑/全局字段越权。 |
| 自审 | 旧 fan-in 字段可能让 Solver 输入审核者 verdict 或 salvage 行；首次 Analyst 输入可能冒充正式方案 | Canonical Solver 过滤审核者记录与旧 salvage 行；其他角色不能提交正式方案；补测批准伪造与 Analyst 写入绕过。 |
| 自审 | 只比对方案镜像不足以保证文档及其 source hash 一致；全局元数据未参与分组来源 | 恢复时校验完整派生文档和哈希，来源包含全局元数据，冻结输入完整校验；补测损坏快照与冻结来源。 |
| 自审 | Python 的 `True == 1` 会掩盖 JSON 类型变化，影响基线、镜像和幂等判断 | 用规范 JSON 身份比较及内容哈希；补测镜像篡改、需求基线变化和类型变化必须产生新版本。 |

自审后未留下已知的本阶段阻塞问题。自审不代表在线模型一次成功率已经证明：本阶段证据针对机制和代码；模型实际输出质量、提示包成本及需求到可执行方案的工序验收属于后续阶段。
