# Orchestrator 重构第一阶段落地记录

本阶段落实《orchestrator-core-redesign-analysis-20261006.md》的第一阶段：统一结构校验、阻断非法方案进入审核和冻结，并提供拥有分组修改权限的独立修复通道。它解决已确认的 RTC 分组失败闭环，不代表后续规划内核重构已经完成。

## 已实现的行为

- `domain/policies/plan_structure.py` 集中定义阻断性结构问题，分组上限继续为六个任务。需求覆盖类问题保留为 Critic 审核提示。入口、分组/任务合并、部分结果挽救、预检和正式方案冻结复用同一阻断规则。
- 首次正式化产生超限分组时，方案不会写入正式状态；通过已有、有限次数的 reply retry 机制重问 Solver。
- 已保存的方案存在分组超限、非法分组标识、投影后的组依赖环或分组归属冲突时，下一次 Solver 派发优先使用 `plan_structure_repair`，不再被局部 finding 的所在组限制。恢复至 Critic/Freeze Check 时，机械预检可直接生成修复事件，无需先调用审核模型。
- 修复使用完整 plan 的传输契约，但仅允许调整 groups 和 item.group_id。任务集合、目标、依赖、验收信号、需求和其他方案字段必须保留；已冻结分组及其文档受到保护。文档 §8 投影后再次校验，防止通过文档改写任务验收标准。
- 新增/改变分组必须携带文档；已有文档沿用版本链。删除旧组对应行，清除改变分组的旧审批，保留未改变分组的文档和审批。分组 ID 集合未改变、成员发生变化时同样失效旧审批。
- 修复通道不会关闭业务 finding。修复越权或格式错误使用有限的回复重试预算；基础设施错误继续沿用原有恢复机制。人工反馈优先级、需求人工审批和冻结后的发布门禁保持不变。
- 正式方案的结构检查覆盖每次冻结，包括 fast track 和已经存在 FROZEN 行的情形。无正式 plan 的旧投影仍保留原有依赖环校验，本阶段不自动转换旧快照。

## 可重复回归

新增 `cmd/test_plan_structure_repair.py` 共 18 个离线测试，事故夹具仅保留真实 ID、分组成员和依赖，业务文字为合成数据，不依赖本地 run 文件。覆盖入口、预检、修复权限、未解决 finding、冻结组保护、审批失效、文档投影、重试预算、基础设施恢复及人工反馈优先级。

其中两个测试驱动真实 `OrchestratorApp`、事件 inbox、effect manager、状态机和持久化仓库：

1. 需求入口 → 首次产生八任务组 → 有界重问 → 三个合法分组 → 审核/冻结/方案输出 → DONE。
2. 旧非法方案恢复至 Critic → 无模型预检 → 完整重分组修复 → 后续方案流程 → DONE。

每个应用测试最多驱动 200 步；发生 BLOCKED、FAILED、意外 HUMAN_GATE 或无工作时立即断言失败，避免回归本身无限等待。关闭人工审批仅用于隔离通知的测试夹具。

旧批次测试的七任务夹具改为两个合法分组，继续保留“只修六个 finding、剩余 finding 不丢失”的原断言。原“第一次冻结后跳过全局检查”测试改为验证后续冻结仍拒绝依赖环，没有通过放宽生产门禁获得通过。

验证命令使用 `rtk proxy python -X utf8 cmd/run_tests.py`。Windows 沙箱无法读取测试临时目录，应用测试和全量测试在获准的沙箱外执行；runner 强制禁止外部通知，未重启或占用运行中的 Nexus 8766 端口。

最终全量结果：**1403 tests，63.300 秒，OK**。针对性机制/应用回归：**151 tests，18.185 秒，OK**。`rtk git diff --check` 通过。全部验证使用保存结果或脚本适配器，模型调用数为零。

## 后续边界

第二阶段仍需建立 canonical PlanRevision 和单一写入接口，再将需求文档变为编译产物；之后推进产物驱动的串行规划主线、业务分组与运行批次分离及版本化迁移。
