# planning-v1 落地与自审记录

## 交付范围

新建 CLI 任务默认正式规划流程；完整方案的唯一写者仍为 Solver，方案版本、编译策略、审批与工序预算可持久化恢复。旧快照保留旧流程，提供显式回退。

固定工序已经落地：需求基线、必要证据、需求方案、人工需求确认、执行细化、整体可执行性审查、确定性发布。业务组不再承担运行批次的 6 项限制及组级依赖调度。工作项依赖 DAG 仍必须合法。

## 验证范围

`test_planning_workflow.py` 包含 21 个测试。实际应用脚本覆盖：

- 五次 agent 派发的成功路径及 JSON、Markdown、验证报告、manifest 发布。
- 超过 6 项的业务组、A→B→C 分布在交错业务组时顺序合法；工作项环仍拒绝。
- 人工需求驳回、修订、重启恢复；执行细化改变需求表面时重新确认。
- Critic 对准确版本的整体审查、语义修复、纯补证直接回审查。
- 用户澄清后回 Solver 消解阻塞未知项；环境前提与引擎错误分别结束。
- 需求基线保护、格式/外部/补证/全任务预算、无进展停止、过期审查拒绝。
- 发布失败、发布重放、文件碰撞、伪成功快照及错误工作流恢复拒绝。
- 生产回复契约与阶段 schema 一致、文件证据原文校验、成功通知包含产物路径。

安全测试入口强制隔离外部通知；没有模型调用，没有重启、停止或占用当前 Nexus 服务。

## 自审与修正

1. 新阶段如果仍使用旧 transport 回复说明，会出现“schema 与提示要求互相矛盾”。改为按当前阶段生成回复说明，并让 structured_output 的 stable_fields 同样取当前阶段。
2. 单纯证据问题如果强制回 Solver，会把未修改正确方案误判为无进展。补证现直接回 Critic，重新审查同一个方案版本。
3. 人工澄清如果回 Critic，阻塞 unknowns 无人修改。执行阶段澄清回 Solver，同时保存用户回答。
4. 需求驳回需要保留反馈历史和旧审批线程锚点。复用原有反馈记录，恢复后仍检查迟到反馈。
5. 成功不仅绑定方案，还绑定证据指纹；发布必须全部文件完成，并持久化完成标记，失败不能转为 PLAN_READY。
6. 新旧图的恢复目的地必须分开；旧任务不能通过 RESUME 意外进入新阶段。恢复检查同时拒绝状态、策略与 workflow 不匹配。
7. 需求确认文档和通知使用正式流程措辞，避免显示旧的“交门下实施”或把生成方案说成已经运行测试。

最终全量回归通过 **1449 项，91.397 秒**；相关测试通过 **59 项，25.550 秒**。一次全量回归中旧 `test_human_gate_is_exempt_from_the_idle_deadline` 遇到 Windows 快照文件占用（WinError 5/32）；该用例连续三次单独复测通过，4.599 秒，随后全量复核通过。此轮未改动共享仓库的文件替换实现；这个并发文件占用风险需如实保留。

测试日志留在忽略目录 `runs/maintenance/20261006-planning-workflow/`，不进入代码提交。
