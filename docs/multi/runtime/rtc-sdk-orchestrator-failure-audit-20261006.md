## 结论

任务 `task-20261006-7c9d13` 的这次失败，主要是机制设计中的约束与修复权限不一致，具体表现为代码在不同阶段采用不同的结构校验规则。它不是“代码审查需求太难”的证据，也不能归因于两次 Solver 没有完成修订。

初始计划的 GRP-001 有 8 个成员，超过内部上限 6，但系统仍接受计划并进入评审。随后系统只派发 GRP-002 的局部修订，却在合并时要求整个计划满足上限。Solver 无权拆分 GRP-001，因此即使把分配给它的工作全部修好，也无法通过合并。这是一条在当前派发权限下不可修复的路径。

本审计没有修改生产代码、恢复原任务或批准计划；只读取持久化记录，以当前代码回放已保存的模型结果。回放新增模型调用为 0，原任务状态未修改。

## 代码发现

### P1：同一结构规则在入口、合并、冻结预检查中的效力不同

`cmd/orchestrator/zhongshu_review_queue.py:33` 定义 `GROUP_MAX_ITEMS = 6`，同文件 527–529 行产生超限问题。

`cmd/orchestrator/domain/policies/solver_plan.py:40` 的阻断问题列表不包含 `GROUP_MAX_ITEMS`。163–172 行的 `structural_integrity_errors` 将此问题过滤掉。初始 Solver 接受路径和评审预检查使用这份过滤结果，因此实际超限计划的阻断结果为空。

但是 `cmd/orchestrator/runtime/agent_effects.py:2380` 在局部修订合并时，同时使用过滤后的结果和完整 `structural_gate` 结果，把所有结构问题作为硬失败。于是同一计划在入口通过，在局部修订后失败；触发失败的 GRP-001 并没有被该修订修改。

回放还进行了纯内存反事实检查：对同一计划模拟各组批准及对应审查哈希，`mechanical_freeze_ready` 返回 `True`，没有阻断项。这只证明冻结的机械预检查没有拒绝该超限结构，不代表实际任务已经冻结或最终完成。该函数位于 `cmd/orchestrator/domain/states.py:5680`。

修复方向：先决定分组上限属于硬约束还是建议，再用一致的策略覆盖计划接受、评审派发、修订合并和冻结条件。不能仅在某个列表补一项就认为问题解决，还必须落实对应的自动修复路径。

### P1：拒绝结果的问题不在派发给修订者的权限内

两次真实 dispatch 都只允许修订 GRP-002 的 ITEM-008、ITEM-010。回放 `_fold_group_revision_payloads` 得到 `patch_errors = []`，补丁所修改的组为 GRP-002；两次 worker 均为 `SUCCEEDED`。

`cmd/orchestrator/domain/policies/solver_plan.py:679` 的 `merge_group_revision_items` 有意保护其他成员和外组条目，局部补丁也没有全局分组拓扑重写权限。这种保护本身有价值，但不能搭配“发现任意外组结构问题，就要求当前局部 worker 通过全局校验”的恢复策略。

修复方向：全局拓扑问题应退回具有对应权限的计划修复阶段，修复后重新评审受影响的表面；局部业务问题继续交给有权修改它的组。派发前应保证至少存在一种被允许的操作能消除拒绝原因。未受影响的有效批准可以保留，但必须按成员与文档哈希验证。

### P2：失败刹车止住了循环，却没有提供正确的恢复路线

`cmd/orchestrator/domain/states.py:318` 对同类失败累计次数，到上限后进入人工门。它避免了无限消耗，但这次把内部结构矛盾交给用户，用户并没有需要决定的业务问题。

修复方向：明确区分传输缺失、回复格式错误、可局部修复的问题、全局拓扑问题和真实的业务不确定性。只有重试可能改变结果时才原样重试；内部结构问题路由至对应修复节点，无法恢复时报告具体工程故障。人工门应说明需要用户决定什么，而不是只提供“重试/批准”。

## 设计层面的判断

把“未提交 C# 代码能否提交”展开成 10 个条目、两份分组文档以及多轮规划、评审、修订，增加了编排失败面。这个判断属于设计评估；本次失败的直接原因仍是上述可回放的规则矛盾，不能单凭条目数量断定整个流程必然失败。

建议为证据充分、范围明确的只读代码审查提供直接路径：固定 diff 范围 → 收集证据 → 审查问题 → 执行适用的非破坏性验证 → 给出提交判断与未验证项。需要跨系统实施、范围澄清或真正业务决策的任务再进入完整规划流程。具体路由条件应由任务性质和证据需求决定，不宜再添加随意的数量阈值。

用做菜的比喻：现在系统先允许“8 份材料”进入工序，又把这部分锁住；下一工序只准修改另外两份，出菜时却要求先前那 8 份最多只能有 6 份。重复下一工序无法解决这个矛盾。
