# 工作流代码自审

本次从可执行代码、异常边界和实际失败记录出发，不以需求文档或已有测试通过作为正确性的证明。范围覆盖锁、任务取消、审批人恢复、卡片回执和运行循环。以下四类缺陷均有修复前失败用例，已修复。

| 严重性 | 缺陷 | 影响 | 修复与证据 |
| --- | --- | --- | --- |
| P1 | Windows 上用 `os.kill(pid, 0)` 探测过期租约的 PID | 存活进程可能被终止；旧测试只用了不存在的 PID，没覆盖存活进程 | 改为只带 SYNCHRONIZE 权限的 OpenProcess 和零超时 WaitForSingleObject，权限不足按存活处理；隔离真实子进程连续探测三次仍存活，退出后允许回收 |
| P1 | 空闲任务的 cancel 只执行一次 step 后立即执行 pending effects | 排在前面的反馈被处理后，任务仍未取消且新模型工作已经发出 | 取消命令先持久入队；在 run lease 下只处理事件直到终态，终态才执行 cleanup/通知，业务 effects 被 guard 跳过；优先处理本地取消，早到回调屏障也不能阻止它 |
| P1 | 审批人恢复的校验在终态保护前，且抛错位于输入异常处理外 | 取消后的恢复、两个排队的恢复或过期依据可直接导致 runtime 异常退出，输入无法正常 ACK | 终态先保护；无效恢复作为拒绝决定持久记录，不更新人员或迁移状态；双恢复竞争只接受第一个 |
| P2 | verify_message 只检查群、机器人 ID 和 card token | 错误 message_id、已删除消息、文本消息或错误 sender_type 可能被当作待绑定回执 | 要求接口成功、准确 message_id、未删除、interactive 类型、app sender、目标群和 gate/page/token 全部匹配 |

Windows 行为依据：[Python 官方 os.kill 文档](https://docs.python.org/3/library/os.html#os.kill)。缺陷存在并不证明此前每轮故障都由它造成；b6bcc7 的日志明确记录的是审批人和 gateway 缺失。

## 验收证据

- 修复前自审回归：3 个失败、2 个运行错误，明确复现上述四类缺陷；os.kill 被 mock 拦截，未对任何业务进程执行破坏性探测。
- 修复后关键模块回归：36 项通过，20.849 秒。
- 补充隔离真实 Windows 子进程、回调屏障取消、双恢复竞争后，自审模块 8 项通过，0.770 秒。
- 最终完整回归：705 项全部通过，93.505 秒；`git -c core.safecrlf=false diff --check` 通过。
- 全部自动化使用 `rtk python cmd/run_tests.py`，屏蔽真实飞书消息；卡片回读测试使用模拟 HTTP。
- live gateway 检查仍为 `process_lock=true, websocket_ready=true, credentials_present=true`。没有重启 Nexus 服务，没有修改业务任务快照或代替用户审批。

## 仍然存在的验收边界

- 真实业务任务仍缺用户指定的审批人。本次没有擅自把任何人设为审批人，没有实测用户点击卡片到 RTC 实施完成的全过程。
- 活跃模型 effect 是同步执行，取消命令可以持久入队，但活跃 runner 要等当前 effect 返回后才消费取消事件。本次修复保证空闲任务和后续 effect 不再被取消流程错误触发，不声称能立即中断已在运行的远端模型。
- 心跳就绪证明连接存在，不等同于已验证卡片事件订阅、审批人身份和全部云文档权限。
- 已运行 Python 进程不会热加载这些修复；新进程使用新代码。当前 gateway 心跳健康，未为加载新代码而中断回调服务。

## 为什么之前的验收没有发现

原有锁测试没有“租约过期但 PID 存活”的 Windows 分支；取消验收前没有排队的人类反馈；恢复验收只测单个成功事件；卡片回执验收只匹配 card token，没有覆盖错误 ID/删除状态。这是验收场景不足，需要明确补齐，不能用测试总数掩盖。
