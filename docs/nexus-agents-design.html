Developer Design Doc

Nexus Agents 项目设计方案

面向开发人员的项目设计说明：讲清楚 Nexus Agents 为什么存在、要解决什么 AI 开发痛点、核心能力有哪些、这些能力的价值是什么，以及未来如何演进。

项目定位

把 AI 开发从“临时提示词 + 手工约定”推进到“可配置、可复用、可评估、可沉淀”的工程体系。

项目级管理 知识库导入 Workflow 编排 模型路由 评估闭环

阅读方式

先看总览，再看痛点与解决方式；如果你是开发者，重点关注“核心功能与设计价值”和“未来方向”。

Why
解决 AI 开发中的上下文不稳定、流程不一致、知识不可审查、结果难复盘。
What
管理 Agents、Rules、Skills、Workflows、Knowledge Base、Routing 和 Evaluation。
Value
让项目知识和流程可视、可校验、可同步、可评估，适合真实项目长期迭代。

目录

1. 项目初衷

Nexus Agents 的目标，不是再造一个“单次对话更聪明”的聊天壳，而是把 AI 开发从临时提示词、口头约定和一次性操作，推进到一个可配置、可复用、可评估、可沉淀的工程体系。

在真实项目里，AI 开发往往不是“模型不会写”，而是“项目上下文不稳定、约束不统一、流程不一致、结果不可复盘”。Nexus Agents 关注的是项目级能力：让 Agent、规则、技能、工作流、知识库、模型路由、评估闭环都能围绕同一个项目持续演进。

对于 btd-client、btd-game-server 这类中大型项目，Nexus Agents 的价值在于：把分散在仓库、文档和人工经验中的 AI 开发资产，变成可观察、可维护、可同步的项目能力。

2. AI 开发中的痛点与解决方式

这一部分建议按“痛点 → 解决方式”的方式阅读，方便快速定位 Nexus 解决了什么问题。

01 上下文不稳定

痛点： AI 每次处理任务时，都可能重复解释项目结构、目录约定、禁止修改的文件、构建方式和常见坑位。

解决： 将约束前置为项目资产，并通过 Loaded Knowledge 机制检查当前任务加载了什么、是否足够支撑执行。

02 工作流不可复用

痛点： bugfix、feature、review、refactor 等流程依赖临时 prompt，质量波动大。

解决： 将工作流沉淀成模板和项目副本，并配合图形化展示与评估结果持续优化。

03 多工具配置割裂

痛点： Codex、Claude Code、.claude、.codex、.agents 各自维护，容易冲突。

解决： 用 Nexus Agents 统一管理项目中的 Agents、Rules、Skills、Workflows 与知识资产。

04 知识库过重或不可审查

痛点： 重型 RAG / 向量检索容易变成“查得到但看不清”。

解决： 知识保持在 Git 内，Nexus 负责导出、展示、校验、路由预览和维护报告。

05 模型路由复杂

痛点： 不同模型后端接入混杂，项目侧难以稳定控制路由策略。

解决： 通过本地 Codex Router 统一路由，把模型选择与项目流程解耦。

06 结果缺少证据与评估

痛点： AI 结果往往缺少证据，失败经验也难沉淀。

解决： 通过 TaskRun、Evaluation、Evidence、Learning Case、Loaded Knowledge 检查形成闭环。

07 模板与项目副本难同步

痛点： 全局模板更新后，项目副本是否过期、是否可安全同步通常说不清。

解决： 用版本、hash、diff、sync preview 和手动同步机制管理关系，避免自动覆盖。

3. 核心功能与设计价值

这里不写成模块清单，而是从“功能为什么存在、它带来的价值是什么”来说明。

A 项目接入与配置管理

设计目标： 导入本地项目后自动识别 Agents、Rules、Skills、Workflows、workflow graph 和项目知识库。

设计价值： 让项目级 AI 配置从“散落文件”变成“可视化资产”。

B 模板库与项目副本体系

设计目标： 维护全局模板，同时允许项目保留自己的副本和定制。

设计价值： 统一标准与项目差异可以同时存在。

C 同步与差异管理

设计目标： 用版本、hash、diff、状态和 sync preview 管理模板与副本关系。

设计价值： 开发者能知道“改了什么、能不能同步、是否会覆盖本地修改”。

D 工作流编排与可视化

设计目标： 将 bugfix、feature、review、refactor 等过程沉淀成 workflow，并图形化展示。

设计价值： 让 AI 开发从“临时聊天”变成“可复用流程”。

E 项目知识库管理

设计目标： 为知识库生成前端展示页，提供 Overview、Validation、Docs、Routing、Maintenance。

设计价值： 知识库既能“看”，又能“验”，还能“维护”，且 source of truth 仍留在 Git 中。

F 模型路由与本地代理

设计目标： 统一 Codex 模型请求，根据模型 slug 路由到不同后端能力。

设计价值： 模型能力与项目流程解耦，按任务灵活分工。

G 执行记录与评估闭环

设计目标： 记录 TaskRun、Evidence、token usage、route metrics，并生成 Evaluation / Learning Case。

设计价值： 结果可复盘，失败可沉淀，优化可反向驱动。

H 统计与健康视图

设计目标： 从项目、workflow、模型、规则、知识维度展示成功率、失败率和稳定性趋势。

设计价值： 帮团队找到不稳定来源和维护重点。

4. 项目优势

1 工程化 AI 资产

把 prompt、规则、技能、工作流、知识、评估统一纳入项目管理，形成可持续建设的工程体系。

2 项目级而非平台级强绑定

项目知识和配置尽量保留在仓库内，Nexus 负责管理、展示、导出和评估，不锁死 source of truth。

3 轻量可审查

优先采用 Markdown、模板、副本、hash、diff、OKF-compatible 知识结构，方便 review 与长期维护。

4 兼容多工具生态

适配 Codex、Claude Code、.claude、.codex、.agents 等入口，适合渐进接入。

5 可渐进落地

可以先接入一个项目、一个 workflow、一个知识库，再逐步扩展，不需要一次性推翻现有方式。

6 面向真实项目规模

面向 btd-client、btd-game-server 这类需要长期维护、持续验证和多轮迭代的项目。

5. 未来方向

建议按阶段理解：先跑通一个项目，再复制到更多项目，最后把能力沉淀成控制台级平台能力。

Phase 1
先在 btd-client 上完成试点。验证导入、展示、校验、路由和维护闭环。
Phase 2
再复用到 btd-game-server。验证同一套机制在不同项目中的适用性。
Phase 3
让 workflow eval 更深入地检查 Loaded Knowledge。不只看结果，也看加载了什么、是否足够、有没有误用。
Phase 4
让 Maintenance Report 从只读走向可提案。从报告演进为 patch proposal，帮助更快转成可执行变更。
Phase 5
将 QAnything / RAG 作为可选辅助层。它们可以辅助检索，但不替代 Git 内的项目知识 source of truth。
Target
让 Nexus Agents 成为项目级控制台。统一管理 AI 开发配置、知识、工作流和评估，让项目在 AI 时代保持可维护、可审查、可演进。
