# 中书省收敛与协议修复设计

## 目标与边界

修复审查确认的中书省流程缺陷，保留“需求转任务”的质量要求。Analyst 提供需求、事实和候选任务；单个 Solver 形成正式任务图；三个 Critic 独立审查；Orchestrator 管理身份、版本、覆盖、问题状态和流转。实现方案仍归门下省。

本方案修订 `2026-09-05-zhongshu-flow-hardening-design.md` 中的语义指纹 quorum、逐 worker 历史快照和候选任务 ID 全量原样保留规则。原设计保留为历史记录，不再作为上述规则的实施依据。

仅修改相关中书省运行代码、本地提示词和本地角色 Skill 文档。保留现有用户改动。不启动服务、不运行测试或 Agent、不发送飞书通知、不修改运行中的任务状态或全局 Codex 配置。外部 Multica Skill 发布不在本次自动操作范围内；不得把本地文档修改报告为已发布到远端。

## 方案选择

1. 推荐：保留状态机和三路并发，统一校验、汇总、问题生命周期与补证上下文。修改面集中，保留已有产物和恢复接口。
2. 改为全串行：可以减少并发汇总复杂度，但仍不能修复错路由、未知项丢失和历史问题无法关闭，不采用。
3. 重写整个工作流：可以统一所有历史协议，但迁移范围和风险过大，不用于这次修复。

## 1. 有效 quorum，而不是不同答案 quorum

- 三个预期 worker 中至少两个独立来源的有效审查才满足 quorum。同一个 worker 或同一请求结果重复到达只能计一次。
- 资格检查先于计票：task、逻辑请求/实际 attempt、worker、状态、角色、phase、revision 和计划 hash 均须匹配当前请求。所有同时提供的版本/hash 别名必须一致；不能依赖相反的字段优先顺序。
- 允许三个 worker 给出相同结论，包括相同版本上的 `APPROVE_FREEZE` 与空 findings。语义指纹仅用于诊断，不决定资格。
- 保留三个 worker 的独立请求和 lens。请求来源只能证明不同调用，不能宣称证明了模型内部推理独立。
- 无 quorum 不冻结。冻结还要求至少两个有效明确批准，没有任何有效审查提出尚未处理的阻断项、补证或人工决策请求。
- 先完成资格、quorum、动作与阻断检查，再持久化最终 verdict，避免中间汇总先写出批准。

## 2. Findings 生命周期与分歧

- 维护完整的持久化问题台账，区分问题身份、各 worker 的观察及 OPEN/RESOLVED 状态。
- 同一 finding 的表述、证据或处理意见不同不是协议损坏：保留原始观察及来源，进入分歧处理，不整批抛弃。
- 不以相同 category/target 下的不同表述直接判断为互斥观点；不同问题可以同时成立。新 finding ID 冲突不得覆盖旧记录。
- 每个 worker 可报告本轮观察或显式复核结论。未提及历史问题不表示关闭；合并后的台账继续保留未解决项。
- 历史问题关闭须有至少两个有效 worker 明确确认解决，附理由或证据，且没有有效 worker 提出仍未解决的反证。Solver 自报 resolved 仅作为待审查响应，不自行关闭台账。
- 冻结阻断以 active P0/P1 为准；已关闭历史 P0/P1 不再阻断。P2/P3 保留为跟进项，但若存在明确的未处理返工请求，不擅自转换为批准。

## 3. 保留动作与正确归属

- 汇总保留每份原始审查以及 findings、questions_for_analyst、missing_evidence、required_change、remaining_blockers、resolution 和对应来源，不把压缩摘要作为唯一权威数据。
- 不再将所有 unresolved 自动转换为 `REQUEST_ANALYST_EVIDENCE`。明确缺事实才交 Analyst；拆分、依赖和分组交 Solver；用户才能决定的问题交 HUMAN_GATE；协议/运行故障保留为故障。
- 混合问题保留完整队列与 owner。当前动作只处理其中一个归属，不得丢掉其他待办。
- 缺少可判定归属时保留未解决状态并请求澄清，不能凭空生成“缺证据”。
- HUMAN_GATE/BLOCKED 在提示词、transport、worker 校验和汇总中一致支持。需求契约阶段返回它们时直接按原动作处理，不把缺失的 requirements 当空契约继续发现任务。

## 4. 定向补证和终止条件

- 在任务上下文中保存唯一需求契约及其版本。普通补证复用契约；只有明确的需求更改或人工决定可以修订契约。
- 补证请求携带当前正式任务图、既有事实、完整问题、Solver 的逐项回复及人工决定。Analyst 只补目标证据，不重新命名全部需求或重新提出全部任务。
- 单独存储 Solver 的补证请求，不要求先存在 Critic review；`NEEDS_MORE_EVIDENCE` 和 `REQUEST_ANALYST_EVIDENCE` 共享明确的上下文传递规则。
- 为中书省增加持久化无进展检测：比较实质任务图、证据与未解决问题，排除 request ID、revision 号、时间戳等传输变化。连续三轮补证/修订没有实质进展，进入 HUMAN_GATE，展示未解决问题及已尝试内容；不自动批准或继续重复派发。
- 首次建立基线不计为无进展。合法的证据新增、问题解决或任务边界变化会重置计数。

## 5. 恢复与部分失败

- 明确区分 logical_request_id 与 attempt request_id。恢复时核对逻辑身份与已保存的实际 attempt 关联，再用实际请求绑定验证 payload；不得直接拿逻辑 ID 与 payload.request_id 比较。
- 验证通过的当前版本结果可以复用；已经失败的 worker 单独补跑。汇总失败不意味着所有成功结果无效。
- 对同版本的无效结果、动作分歧或身份冲突，记录拒绝原因及原始产物引用。请求查询仍作为未完成请求的恢复途径，不假定本地结果缺失就可以重复派发。
- 旧格式不能建立可信关联时不猜测匹配，保留记录并走已有恢复/故障路径。

## 6. 需求覆盖与无损任务图

- 保留任务级和全局 unknowns、risks、constraints、protected_paths、证据来源及 blocking 属性。不用字符串化或字段白名单静默丢掉结构化未知项。
- 重新校验正式图的每个可执行 must 需求均有对应任务；仅保留 requirements 列表或候选 ID 不算覆盖。
- Solver 可合并、拆分候选任务，但须提供从候选任务到正式任务的显式来源映射。未被映射的候选不能静默消失；已映射且需求/证据/未知项完整保留的不再要求沿用原 ID。
- 同 task_key 但含义不同的候选保留为候选冲突交 Solver 处理，不直接合并；不同 task_key 的类似工作由 Solver 判断，程序不以文本相似度猜测等价。
- 阻断性未知项必须解决或进入明确人工决策，不能以凑齐 worker 数量或捏造任务掩盖。全部需求都暂时无法拆解时，也允许进入缺口处理，不先报“无任务”的格式错误。
- 规划阶段需要定义可执行的调查/测量任务和验收条件，不要求在冻结前执行这些任务，不把“审查优化空间”自动变成授权实施优化。

## 7. 统一提示词与 Skill

- 中书省 Analyst、Solver、Critic 各保留一份当前权威职责与模式协议；移除与当前职责冲突的旧运行示例，保留必要证据、安全边界和人工决策规则。
- 需求契约、任务发现、定向补证、正式图修订和审查的成功/非成功动作由相同规则定义，transport 与校验器消费一致定义。
- 提示词明确相同审查结论合法、问题关闭标准、任务级未知项保留、候选映射及补证归属。不要求 Agent 为满足“独立性”刻意制造差异。
- 本地 Skill hash 标识文档内容，不等于外部 Agent 已加载该版本；交付时明确本地与外部发布的边界。

## 实施位置

- `cmd/orchestrator/zhongshu_parallel.py`：有效审查汇总、问题观察/状态、动作和信息保留、Analyst 合并。
- `cmd/orchestrator/app.py`：quorum 顺序、阶段结果恢复、需求契约复用、反馈传递和无进展处理。
- `cmd/orchestrator/states.py`、`zhongshu_solver_contract.py`：角色提示词、补证与修订规范、需求覆盖和候选映射校验。
- `cmd/orchestrator/context.py`：兼容旧状态的进展字段，默认值不改变旧记录。
- `cmd/orchestrator/parallel_runtime.py`、`adapters.py`、`prompt_bundle.py`：仅调整本修复需要的身份/动作协议，不改通知发送行为。
- `docs/multi/zhongshu-*-skill.md`：统一本地角色规则。
