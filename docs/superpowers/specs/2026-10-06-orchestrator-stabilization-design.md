# Orchestrator 工序稳定化

用户已在审查结论和工序建议后批准“按你的建议处理”。本设计落实该方向，保持当前三角色、单份需求审批和组文档模型。

## 选择与边界

采用现有状态机内的定向修复。单纯继续增加重试无法纠正错误记账；重写流水线会扩大验证面，本轮不采用。

生产流程仍须对整份需求文档批准后才进入门下省。局部隔离表示：一个组停滞时，其他可审组继续完成并保留批准；全部可推进工作耗尽后汇总待决组。脚本关闭人审时继续支持已有增量冻结。

## 修订与补证

只在有效 Solver 修订交付后的一次 Critic 复审中消耗该批次的 stuck 计数；后续补证复审不重复消费旧批次。新正式方案没有失败修订批次。旧快照无批次时，Critic 请求补证不得使用兼容的全 finding 计数。补证仍受独立的有界无进展守卫约束，真实反复无进展不能无限运行。

## 局部停滞

停滞 finding 或 item 明确归属于一个组时，只停泊该组。新增 Critic 自循环用于继续其他待审组；派发排除停泊、冻结及仍持有批准的组。无可审组但有可冻结组时，脚本增量流程先进入冻结检查；生产全部需求未闭合时汇总组级人闸，保留其他组批准。无法定位归属或全局错误仍保留全任务阻断。

## 门下省有效进展

从已验证文档的阻断建议和待确认反驳中计算问题 ID 集合。关闭旧阻断即为进展，即使新阻断使数量相等；文档或 worker fingerprint 改变本身不能证明解决问题。持久化上轮审查的问题集合；没有该字段的旧记录从已保存文档恢复，无法恢复时沿用有界数量判据。格式修复不占实质修订预算。

## 需求边界

提取契约只来自原请求；禁止为了凑数量添加方向、覆盖率或时长目标。新增带数量限定的验收必须在原请求中有相应数量依据，机械拒绝已知的无依据数量约束。关于完整性、性能与正确性的推导须说明审查范围、假设和待验证项，提示词不得把这些推导包装成用户要求。该检查不能替代语义审查，保留人工审查需求范围。

## 验收

新增真实状态类回归：补证不误记修订、有效修订只计一次、局部停滞继续其他组且不绕过生产人审、同数量旧问题关闭不误判停滞、真正无进展仍有界、无依据的至少三个方向被拒。

固定小需求：审查本仓库 orchestrator 的补证/修订路由，交付现状、一个具体缺陷、最小修复步骤和验收方法，不修改业务、不增加无依据数量要求。脚本使用真实 OrchestratorApp 验证需求提取、格式纠错、方案审查、必要的模拟人审及门下省最终方案，连续运行并记录产物。真实模型验证与脚本验证分别记录，未经真实完整闭环不得宣称生产稳定。

验证统一通过 python cmd/run_tests.py，禁止外部飞书通知及真实用户审批；不重启当前 Nexus，不写既有任务快照，不改全局模型配置。
