# 工作流自动验收测试机器人（日志取证与证据门禁修复）需求

> 状态：草案，待用户审核。
> 上位需求：`2026-10-07-zhongshu-requirements-workflow-requirements.md`。本需求针对该需求实现后的自动验收与缺陷闭环，不改变其业务语义。

## 1. 背景

requirements-v1 工作流按封闭状态机推进：需求侧 `REQ_INTAKE → REQ_ANALYZE → REQ_DRAFT → REQ_VALIDATE → REQ_REVIEW → REQ_REVIEW_PUBLISH → REQ_CONFIRM_WAIT → REQ_APPROVAL_VERIFY → REQ_PUBLISH → REQ_HANDOFF`，经 `MENXIA_REQUIREMENTS_INTAKE → MENXIA_GROUP_SOLVER → MENXIA_GROUP_ANALYST → MENXIA_GROUP_CRITIC → MENXIA_GROUP_GATE` 到 `DONE`；旁路与系统状态包括 `REQ_CLARIFY_PUBLISH/REQ_CLARIFY_WAIT`、`REQ_EVIDENCE`、`REQ_RETRY_WAIT`、`REQ_ENGINE_ERROR`、`REQ_BLOCKED`、`REQ_CANCELLED`。每一步由引擎单事件推进，journal 记录 sequence 严格 +1。

现有测试体系已有约 97 个脚本化测试经 `python cmd/run_tests.py` 驱动真实 `OrchestratorApp`，零模型 token 验证机制。但脚本化测试全绿的同时，真实运行持续出现各类故障。以 2026-10-07 当天日志为证：13 次真实任务启动无一推进到门下省；出现 16 次 `REQ_ANALYZE → REQ_RETRY_WAIT` 往返、6 次 `REQ_ANALYZE → REQ_ENGINE_ERROR`、多次 `REQ_BLOCKED` 进入与自环转换。定位一次真实故障需要人工在多个证据源之间交叉比对，成本高且不可重复。

观测缺口实例（真实日志摘取）：

- `DOMAIN_TRANSITION` 对引擎失败只记录 `reason=ENGINE_FAILURE`，不携带错误码、来源效果或失败对象，单看该行无法判断失败原因；
- `REQUIREMENTS_EFFECT_FAILED` 记录 `reason=PREREQUISITE_MISSING`，不说明缺少哪个前提；
- 同一日志目录混有脚本化测试与真实任务的记录，人工归因困难。

因此需要一台自动验收机器人：按状态机逐步验收每次运行，通过日志与持久化证据判定结果；日志不足以判定时推动补日志；只有拿到真实证据证实缺陷才进行修复，修复后自动复验。机器人的核心纪律是：**没有证据不下结论，没有证实不修复**。

## 2. 目标

1. 每次运行（journal 回放、脚本化或真实）都得到一份逐步验收结论，每个状态转换都有判定：通过、不通过、不可判定；
2. 验收结论必须引用真实证据（journal、日志、产物），不接受推测性结论；
3. 日志不足以判定时产出可执行的补日志需求，使每一步都可判定；
4. 只有满足证据标准的缺陷才进入自动修复，修复后自动复验并回归，失败则回退；
5. 回放与脚本化验收零模型 token；允许消耗 token 运行真实测试，live 运行是一等验收场景：发起前记录目的与场景，运行后记录 token 消耗与结论，事后可审计；
6. 输出用户可读的验收报告与可复核的证据包；
7. 定时巡检运行中的任务：周期性查看日志与 journal，发现可证实的缺陷时立即停止该运行，防止继续消耗 token 与扩大污染，随后进入修复流程。

**验收范围（用户指定）**：只验收中书省需求侧，即 `REQ_INTAKE` 至 `REQ_HANDOFF`（含澄清、确认门禁）。门下省（`MENXIA_*`）尚未重新设计，不在验收范围内：到达 `REQ_HANDOFF` 即视为中书省一次完整通过；门下省状态仅观察不判定，不为它产出验收结论或修复需求。

## 3. 被测对象与证据源

被测对象是 requirements-v1 工作流的一次完整或部分运行（OrchestratorApp 进程及其全部产物），验收边界到中书省 `REQ_HANDOFF` 为止（见第 2 章范围）。

证据源按优先级与成本排序：

1. `runs/<task_id>/workflow-events.jsonl`：事件溯源 journal（transition、effect_intent、effect_running、effect_result、domain_event、domain_event_ack），记录顺序即真实推进顺序，是逐步验收的主证据；
2. `runs/<task_id>/workflow-state.json`：当前快照，用于核对 journal 终点与快照一致；
3. `multica/orchestrator-*.log`：进程日志（事件名 + JSON 元数据），用于核对 journal 之外的运行时行为（卡片链路、并发租约、代理回复解析、效果执行）；
4. `runs/<task_id>/artifacts|transport|requirements/`：产物与调度记录，用于内容级验收（草案、评审文档、交接产物、进度通知）；
5. `runs/requirements-gateway.sqlite`：卡片网关收件箱、回调与审批屏障记录；
6. 真实运行时的代理派发回复与 multica CLI 记录：最昂贵，仅在以上证据无法回答时使用。

证据归因规则：一切证据按 `task_id` 归因；跨任务日志行不参与验收判定，日志中无法归因的行记为观测缺口而非判定依据。

## 4. 每步验收要求

### 4.1 状态机合法性（所有状态的公共验收）

- 每个观察到的转换必须属于封闭边表（`domain/requirements/transitions.py` 的 EDGES 及系统性边）；未定义的状态、事件或组合判为不通过；
- journal 的 sequence 必须线性且严格 +1，无缺口、无回退、无重复提交；
- journal 重放终点必须与 `workflow-state.json` 一致；
- 自环转换（如 `REQ_CONFIRM_WAIT → REQ_CONFIRM_WAIT`、`MENXIA_REQUIREMENTS_INTAKE` 自环）必须能从证据中说明触发事件与幂等依据，说明不了判为可疑。

### 4.2 每状态验收清单

每个业务状态定义自己的通过标准，判定基于证据而非对模型输出的主观评价。至少覆盖：

- `REQ_ANALYZE`：分析契约有效、证据引文逐字核验有结论；被拒派发能看到拒绝类别与修复指引；需要澄清时产出结构化问题批次；
- `REQ_DRAFT`：草案契约有效、骨架章节齐全、用户确认内容与模型建议在证据中可区分；
- `REQ_VALIDATE`：机械校验有明确结论及原因；
- `REQ_REVIEW` / `REQ_REVIEW_PUBLISH`：评审路由有依据（通过、修订、补证、需用户决定），发布效果有评审印记且发布产物可读回；
- `REQ_CLARIFY_PUBLISH` / `REQ_CLARIFY_WAIT`：卡片发布有回执，等待态进入与退出事件明确（答案提交、刷新、超时归属清晰），未答必答项时不得推进；
- `REQ_CONFIRM_WAIT` / `REQ_APPROVAL_VERIFY`：确认绑定正在审核版本的 digest，核验失败保留结构化原因（如 STALE_APPROVAL）；
- `REQ_PUBLISH` / `REQ_HANDOFF`：发布不可变写入完成、交接持久化完成；
- `MENXIA_*`：**不在验收范围**（门下省尚未重新设计）。运行若进入门下省，只记录状态轨迹供观察，不判定、不产出修复需求；为节省 token，可在到达 `REQ_HANDOFF` 后停止运行；
- 终态（DONE、FAILED、REQ_CANCELLED）：进入条件与全程证据一致，CANCELLED 必须能对应取消来源；
- 系统状态（REQ_RETRY_WAIT、REQ_ENGINE_ERROR、REQ_BLOCKED）：进入必须带结构化原因，退出必须说明恢复依据。

派发结果的三重验收（契约校验、语义校验、证据引文核验）必须能在证据中看到结论；被拒派发必须能看到拒绝类别与修复指引。

每步验收结论必须可判定：无法判定时必须归因到具体观测缺口，不得默认为通过或失败。

## 5. 日志完整性与补日志要求

### 5.1 最小日志契约

- 每个状态转换：`DOMAIN_EVENT_DISPATCH`（事件与上下文）与 `DOMAIN_TRANSITION`（before、after、event、action、reason、effects 数）齐备，且 journal 中每个 transition 记录都能在日志中找到对应行，反之亦然；交叉不一致记为观测缺口；
- 每个效果：`REQUIREMENTS_EFFECT_STARTED / FINISHED / FAILED` 生命周期齐备；FAILED 必须携带可行动原因（效果名、错误类别、缺失前提清单或超时对象），只有错误类别没有对象的记为观测缺口；
- 系统性转换（进入 REQ_RETRY_WAIT、REQ_ENGINE_ERROR、REQ_BLOCKED）：必须携带错误码、来源效果、尝试次数与预算状态；
- 卡片链路：发送、回调、拒绝、重复、解析失败均有事件，且能通过 message_id / gate token 相互关联。

### 5.2 观测缺口的处理

- 机器人发现证据不足以判定时，判为观测缺口，不猜测结论，不改代码语义；
- 观测缺口转化为补日志需求：事件名、应携带字段、写入位置、该日志对判定的必要性；补日志只增加观测，不改变工作流语义、失败与恢复行为；
- 补日志落地后必须在脚本化测试中验证该事件可被断言（进程内 `assertLogs` 或日志文件断言）；
- 日志脱敏约束维持不变：只记录标识符、计数与错误码，不记录正文、密钥或用户内容。

## 6. 缺陷判定与证据标准（核心）

### 6.1 判定分级

- 通过：该步全部验收点有证据支持；
- 观测缺口：证据不足以判定，已产出补日志需求；
- 环境故障：外部依赖失败（multica CLI、网络、飞书 API、磁盘），不属于代码缺陷，报告并保留证据；
- 疑似缺陷：出现与预期不符的现象，但未满足证实标准；
- 确认缺陷：满足 6.2 全部证据标准，允许进入修复。

### 6.2 证实缺陷的证据标准（全部满足才可修复）

1. 期望与实际都可引用：期望来自状态机定义、契约或上位需求文档，实际来自 journal、日志或产物，双方都有出处；
2. 可复现：缺陷在至少两个独立证据源同时出现，或通过 journal 回放、时间旅行恢复（复用现有快照复制加 `--resume` 机制）、脚本化场景确定性复现；单次偶发且无法复现的保持疑似；
3. 根因定位：能指出证据中的具体位置（文件与记录），说明缺陷如何从根因传导到观察到的失败；
4. 排除解释：已排除环境故障、模型行为的合理偏差与测试自身错误。

### 6.3 分类边界

- 模型输出质量问题（引文失真、格式错误、内容缺陷）进入设计内修复路径的，属于机制正常工作，不是缺陷；机制未按设计处理它才是缺陷；
- 脚本化测试与真实运行结论冲突时，优先用真实运行证据回放定界，并检查脚本假设是否过时，而不是默认代码有错或测试有错。

## 7. 自动修复与自动复验要求

### 7.1 修复进入条件

- 只有确认缺陷进入修复阶段；疑似缺陷只产出证据包与修复建议；
- 修复必须作用于证据指向的根因；修复者必须有权修改导致拒绝的问题，不能只允许改一处却要求它消除另一处受保护内容的错误。

### 7.2 修复约束

- 不放宽任何不变量：审批棘轮、机械 freeze、哈希审批、版本 digest 绑定、外部通知禁用开关、状态机封闭边表不可为消除失败而修改；
- 修复若改变状态机语义或契约，必须同步更新对应脚本化测试与文档，不允许测试追着实现漂移；
- 修复有预算限制：同一根因不因无新证据的重复尝试而反复修改；连续两次修复未通过复验则停止并升级为人工处理。

### 7.3 自动复验

- 修复后必须依次通过：原场景复跑（与取证时相同证据源与场景）、相关脚本化测试（经 `python cmd/run_tests.py`，强制禁用真实通知）、被修改面的邻近测试；
- 复验不通过则回退修复并保留回退记录，不允许保留部分修复；
- 修复、复验、回退全程留痕：改动内容、依据的证据条目、复验结果。

### 7.4 修复入库

- 修复复验通过后，机器人将修复提交到 git（当前分支，不自动推送远端），保证可回滚；
- 提交只包含修复相关文件；提交信息必须写清：确认缺陷的证据引用、根因、修复内容、复验结果（原场景复跑与回归测试结论）；
- 提交前核对工作区：不夹带与修复无关的改动；回退修复时优先使用 git revert 对应提交。

## 8. 与现有测试体系的关系

- 不替代现有体系：脚本化测试仍是机制回归基准，机器人的机制场景直接复用其脚本化 adapter 与 fixtures；
- 机器人新增的能力是：跨证据源交叉验收、逐转换判定、观测缺口管理、证据门禁的缺陷证实与修复闭环；
- 运行纪律：
  - 一切测试经 `python cmd/run_tests.py` 或独立入口运行，强制 `NEXUS_TEST_NO_EXTERNAL_NOTIFICATIONS=1`，禁止真实外发；
  - 真实验证实例使用独立端口（如 18766），绝不触碰、停止或重绑活跃服务的 8766；
  - live 运行允许消耗 token：发起前记录目的与场景，运行后记录实际消耗、轮次与结论；回放与脚本化仍是日常机制回归的默认档，但不得以节省 token 为由跳过必要的真实验收。

### 真实测试运行手册（标准 live 场景）

- 工作目录：仓库 `multica/` 目录；
- 每次真实测试前必须先清理重置：运行 `multica/cleanup-my-issues.ps1`（带当前会话 cookie），删除当前用户在 multica 上全部 open issue；清理后核对删除结果，清理失败不得启动新测试；cookie 过期时明确报错要求人工刷新，不得跳过清理；
- 启动命令：`python -X utf8 cmd/review_orchestrator_v2.py --project <项目ID> --project-type unity --task-type review --runs-root runs --poll-interval 15 --timeout 900 --new "<初始请求文本>"`；communication 默认 feishu，澄清卡片真实发布，由用户在飞书回答；
- 机器人在该场景中的职责：执行清理并核对、启动运行、随后按第 9 章对该任务定时巡检、按第 6 章判定；
- cookie 等凭据属于环境输入，只从环境或用户会话获取，不写入代码、文档与报告。

## 9. 定时巡检与停止要求

### 9.1 巡检形态

- 机器人除单次验收外，以固定间隔对运行中的任务做定时巡检：读取该任务 journal 的增量与日志尾部，执行第 4 章检查的轻量版（状态机合法性、效果配对、日志交叉核对）；
- 巡检只读取证：不加锁、不写任务目录、不干扰被测进程；单次巡检自身耗时应远小于巡检间隔；
- 正常等待不是问题：任务处于有明确等待原因的状态（REQ_CLARIFY_WAIT、REQ_CONFIRM_WAIT 等）时，巡检不得将等待判为缺陷，也不得停止。

### 9.2 停止条件

- 巡检发现满足第 6.2 章全部证据标准的确认缺陷时，立即停止被测运行，防止继续消耗 token 与扩大污染；
- 停止使用被测系统自身的取消与终止路径，保证 journal 完整落盘、证据可复核；停止动作必须留痕：时间、触发停止的缺陷证据引用、停止前最后一个转换；
- 未满足证据标准的疑似缺陷不触发停止，只记录并继续观察；观测缺口产生补日志需求，同样不触发停止。

### 9.3 停止后的修复与恢复

- 停止条件即确认缺陷，证据门禁已经满足，停止后直接进入第 7 章修复流程：定位根因、修复、复验；
- 修复复验通过后，恢复方式按影响面决定：修复不影响已完成步骤时，可从停止前快照以时间旅行方式续跑；修复影响状态语义或契约时，重新发起运行，并沿用巡检期间积累的有效证据（用户答案、已确认选择）；
- 恢复后巡检继续，直至任务到达终态或进入等待态。

### 9.4 门禁直通（自动应答）策略

- 用户已授权：巡检与验收场景下，机器人代用户通过人工门禁，测试不得因等待人工而阻塞；
- 遇到澄清卡片（REQ_CLARIFY_WAIT）：机器人从证据中读取问题与推荐项，按推荐选项自动提交答案（经本地应答通道，如 `--resume <task> --answer-file`）；没有推荐项但有默认假设时采用默认假设；两者都没有的问题记录证据并说明，不阻塞其余问题的提交；
- 遇到草案确认门禁（REQ_CONFIRM_WAIT）：机器人以显式批准动作代用户确认（绑定正在审核版本的 digest），不使用沉默或推荐选项冒充批准；
- 全部代答与代确认必须留痕：问题 ID、选择的选项、是否推荐项、提交回执；报告中醒目标注哪些决定是机器人代作的；
- 自动应答被工作流验收拒绝（如授权校验、STALE_APPROVAL）时，按证据处理并报告，不绕过工作流自身校验。

### 9.5 巡检留痕

- 每次巡检留下最小记录：时间、任务、读取的 journal 位置、结论（无发现、观测缺口、疑似缺陷、确认缺陷并已停止）；无发现的巡检只累计计数，不生成报告正文；
- 巡检发现的问题与单次验收使用同一判定表与证据包格式，避免两套标准。

## 10. 机器人自身的工作阶段

机器人按以下阶段推进，每阶段有进入与退出条件。机器人有两种工作形态：单次验收按以下阶段完整执行一次；定时巡检是第 2 至第 4 阶段的循环（见第 9 章），触发停止后从第 5 阶段继续。

1. 计划：选定被测场景与证据源等级（journal 回放、脚本化、时间旅行、live），说明选择理由；live 场景与其他场景地位相同，选择只取决于该场景回答什么问题；
2. 运行与采集：执行或定位运行，收集证据包（journal、日志窗口、快照、产物清单）；
3. 逐步验收：按第 4 章逐转换判定，产出判定表；
4. 判定：按第 6 章分级；观测缺口转补日志需求，疑似缺陷转证据包，确认缺陷转修复；
5. 修复与复验：仅对确认缺陷，按第 7 章执行；
6. 报告：用户可读的结论、判定表、证据出处、修复与复验记录、遗留观测缺口。

- 机器人自身崩溃后可从证据重建验收进度，不依赖自身持久化状态；
- 报告与证据包按运行保留，不被后续运行覆盖；报告落盘供用户查阅，不占用真实飞书通知链路。

## 11. 验收标准

### 机制对齐

- 对现有脚本化场景，机器人的逐步判定与现有测试断言结论一致；
- 能对一个真实运行目录只依据证据重建完整状态轨迹并逐转换判定，全程零模型 token。

### 中书省完整闭环（live 一等场景）

- 一次真实运行从中书省 `REQ_INTAKE` 推进到 `REQ_HANDOFF`，全部转换逐判定通过，澄清门禁与确认门禁由机器人按第 9.4 节代答留痕；到达 `REQ_HANDOFF` 即为中书省一次完整通过。

### 缺陷证实

- 注入一个已知缺陷（非法转换、效果丢失、失败原因缺失等）后，机器人能以可复现证据证实并定位根因，而不是凭单点现象断言；
- 人为制造疑似但不可复现的现象时，机器人保持疑似分级，不进入修复。

### 观测缺口

- 删除某一关键日志事件后，机器人将该步判为观测缺口并产出可执行的补日志需求；补日志后该步恢复可判定。

### 修复闭环

- 对一个确认缺陷，机器人完成修复、原场景复验与回归测试，全程留痕；复验不通过时回退。

### 巡检与停止

- 对一个携带已知缺陷的运行，巡检能在轮询间隔内发现、证实并停止，停止时 journal 完整、证据包可复核；
- 正常等待态与无缺陷运行不会被巡检停止；疑似缺陷只记录不停止；
- 停止并修复复验通过后，任务能恢复或重新发起，且沿用巡检期间积累的有效答案与确认记录。

### 运行纪律

- 全流程无真实外发、不触碰活跃服务端口、live 运行有目的与消耗记录。

## 12. 非目标

- 不修改工作流业务语义，不放宽审批与冻结条件，不自动批准任何内容；
- 不验收门下省（`MENXIA_*`）：该阶段尚未重新设计，机器人不为其判定、修复或产出报告；
- 不替代用户对需求草案内容的审核；
- 不做性能压测、容量规划或并发调优；
- 不自动提交、推送或部署代码；修复以本地工作区变更与测试通过为边界；
- 不处理已归档的 legacy Zhongshu 工作流与历史任务迁移；
- 不承诺固定缺陷发现率、修复成功率或检测时长；
- 不新增飞书卡片功能；机器人不直接向用户发送消息；
- 巡检对运行中的任务只读取证与执行停止，不修改任务状态、数据或运行参数；除停止外不实时干预运行。
