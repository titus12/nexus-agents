# Go 测试执行规范

先读取 `.claude/rules/test-driven-change.md`。该规则决定测试是否必要、
测试的长期价值和例外条件；本 Skill 仅规定 Go 的测试技术与验证顺序。

## 用例设计

- 同一业务规则的多个输入、边界和错误输入，优先使用表驱动测试和子测试。
- 仅当业务语义、失败原因或诊断责任明显不同，才拆分为独立命名测试。
- 断言导出的行为、返回错误、领域状态和跨边界契约；不要断言私有 helper、
  局部变量或偶然的内部调用顺序。
- 新增、扩展、合并或删除测试时，按共享规则填写 `Test decision` 证据。

## 隔离与确定性

- 对时钟、随机数、文件系统、网络和外部服务使用项目既有 fake、stub 或边界
  注入方式。
- 避免真实网络、`time.Sleep`、未受控的当前时间、全局随机状态和依赖执行顺序。
- 不要为测试专门导出生产 API，也不要为简单内部协作过度创建 interface。
- mock 只验证明确的外部边界契约，不验证实现细节。

## 验证顺序

先运行定向测试，再按影响面扩大范围：

```text
go test ./path/to/package -run TestName -count=1
go test ./path/to/package -count=1
go test ./...
```

使用项目已有的 build tag、测试命令和静态检查约定。最终报告只能列出实际运行过
的命令、结果、未验证范围和风险；计划中的命令不能写成已通过。
