# 审核反馈处理与动态纳入规范

> 触发：收到审核反馈 / 审核完成后发现 rules 未覆盖的风险模式
>
> §1 反馈处理 §2 动态纳入机制 §3 纳入流程 §4 原则

## §1 反馈处理

收到用户、reviewer 或自动审核反馈时：

1. 先完整阅读所有反馈，不立即改代码
2. 不清楚的反馈先复述理解或提问澄清
3. 对照真实代码、测试和需求验证每条建议
4. 将反馈分类：
   - 正确且必须修
   - 正确但可作为后续优化
   - 不适用或技术上不成立
   - 信息不足，需要澄清
5. 已确认的问题逐项修改，并运行相关验证
6. 对不成立的反馈，用简短技术证据说明原因

Review 反馈是待评估输入，不是必须盲从的命令。

如果反馈要求“完整实现”某个当前未使用能力，先搜索实际调用路径；未使用时优先考虑删除或暂缓，而不是扩大实现范围。

## §2 动态纳入机制

审核过程中（reviewer 或用户）发现的新风险模式，如果现有 rules 未覆盖，主动建议纳入规范。

## §3 纳入流程

1. 向用户提示：
   ```text
   审核中发现新的风险模式：[描述]
   当前规范未覆盖此类问题。是否纳入 [对应 rule 文件]？
   ```
2. 用户确认 → 更新对应 rule 文件
3. 用户拒绝 → 记录到“已评估不纳入”

## §4 纳入原则

- 只纳入重复出现或高风险的模式（偶发性不纳入）
- 纳入时给出具体可执行的检查规则
- 每条规则标注负责检查的 reviewer 角色
- 规范只增不减（除非用户确认已过时）
