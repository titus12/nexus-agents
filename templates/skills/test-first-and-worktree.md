# 测试优先与隔离工作区

> 触发：核心逻辑开发 / bugfix / 重构 / 中大型改动
>
> §1 测试优先 §2 适用与例外 §3 隔离工作区 §4 检查清单

## §1 测试优先

对新业务逻辑、bugfix、公共函数、状态机、边界复杂逻辑，优先采用 test-first：

1. 先写或更新描述目标行为的测试
2. 运行测试，确认因预期原因失败
3. 写最小实现让测试通过
4. 运行目标测试和相关测试
5. 仅在测试保护下重构

bugfix 优先补回归测试；如果无法补测试，必须描述复现路径和替代验证方式。

## §2 适用与例外

优先 test-first 的场景：

- 新业务规则、数值计算、奖励、扣减、状态迁移
- parser / validator / transformer
- 公共 API、复用工具函数
- 曾经回归过的问题
- 难靠人工检查覆盖的边界条件

可不强制 test-first 的场景：

- 纯文档、注释、静态文案
- 机械重命名或格式化
- 生成文件
- 探索性 spike（后续稳定化时补测试）
- 无测试支撑的遗留区域，但必须给出替代验证

跳过测试时，要说明原因、风险和实际执行的验证。

## §3 隔离工作区

中大型改动前优先使用隔离分支或 worktree，避免污染当前工作区。

适用场景：

- 跨多个文件或子系统
- 改动需要多轮迭代
- 当前工作区已有无关修改
- 实验性方案
- 多 agent 并行修改

创建新 worktree 前：

1. 先检查当前环境是否已经是隔离工作区
2. 查看 `git status`，不要覆盖用户已有修改
3. 项目内 worktree 目录必须被 `.gitignore` 忽略
4. 无法创建时，明确说明并在当前目录谨慎执行

## §4 检查清单

- [ ] 该改动是否需要 test-first？如果跳过，原因是什么？
- [ ] bugfix 是否有复现路径或回归测试？
- [ ] 是否需要隔离分支 / worktree？
- [ ] 是否确认不会覆盖用户未提交修改？
- [ ] 是否已运行目标测试、构建或替代验证？
